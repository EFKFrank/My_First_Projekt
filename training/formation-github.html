01 — Introduction

Chaque commit est un instantané,
pas une différence.

Git modélise l'historique comme un graphe orienté acyclique (DAG) d'objets identifiés par hachage SHA-1 — pas une suite de patchs appliqués les uns après les autres.

Git

Un système de contrôle de version distribué : chaque clone contient l'historique complet, sous forme d'objets stockés dans .git/objects (blobs, trees, commits).

GitHub

Un hébergeur de dépôts Git qui ajoute une couche collaborative : pull requests, issues, CI/CD (Actions), gestion des accès — sans modifier le fonctionnement de Git.

  • Working directory — les fichiers tels que vous les éditez sur le disque.
  • Staging area (index) — la prochaine photo en préparation, construite avec git add.
  • Repository (HEAD) — l'historique déjà validé, sous forme de commits immuables.

02 — Vocabulaire

Six objets et références à connaître

Le modèle de données de Git repose sur peu de primitives. Une fois posées, tout le workflow devient prévisible.

repository

Le dossier .git : une base d'objets adressés par hachage (blobs = contenu, trees = arborescence, commits = snapshots).

commit (SHA)

Objet immuable identifié par une empreinte SHA-1, pointant vers un tree et vers son ou ses commit(s) parent(s).

branch

Une référence mutable (un fichier de 41 octets) qui pointe vers un commit. Créer une branche ne copie aucun fichier.

HEAD

Référence symbolique vers la branche courante. En état detached HEAD, elle pointe directement vers un commit.

staging area (index)

Zone intermédiaire entre le répertoire de travail et le prochain commit ; alimentée par git add.

remote

Un alias vers l'URL d'un autre dépôt (origin) ; git fetch télécharge ses références sans toucher à la branche locale.

03 — Mise en route

De zéro à un premier commit signé

Quatre étapes pour une configuration locale correcte, avant le premier push.

  1. 01

    Générer une clé SSH

    ssh-keygen -t ed25519 -C "email", puis ajouter la clé publique dans Settings → SSH keys sur GitHub.

  2. 02

    Initialiser ou cloner

    git init pour un nouveau projet, git clone git@github.com:… pour un dépôt existant (protocole SSH).

  3. 03

    Configurer l'identité globale

    git config --global user.name/user.email et init.defaultBranch main.

  4. 04

    Écrire un .gitignore

    Dès le premier commit, pour exclure node_modules/, .env, artefacts de build et secrets locaux.

04 — Workflow

Le cycle d'une branche de fonctionnalité

De la création de la branche jusqu'à sa publication, en passant par un index construit hunk par hunk.

$ git switch -c feature/menu-fix          # nouvelle branche depuis HEAD
$ git status                             # état du répertoire de travail
$ git diff                               # revoir les changements non indexés
$ git add -p                             # indexer par hunks, sélectivement
$ git commit -m "fix(menu): corrige le lien cassé"
$ git push -u origin feature/menu-fix    # publie, lie le tracking
$ git log --oneline --graph --decorate  # visualiser le DAG

05 — Collaboration

Fusionner sans perdre le fil de l'historique

GitHub ajoute une couche de revue et d'automatisation au-dessus des primitives de fusion de Git.

pull request

Compare deux références (branche vs main) ; GitHub calcule un diff à trois points via le merge-base commun.

code review

Commentaires ancrés sur des lignes précises d'un commit ; les threads doivent être résolus avant la fusion.

merge / rebase

merge crée un commit de fusion (historique fidèle) ; rebase réécrit les commits sur une nouvelle base (historique linéaire).

  • Un conflit se résout en éditant les marqueurs <<<<<<< / ======= / >>>>>>>, puis git add + commit (ou rebase --continue).
  • Les branch protection rules imposent une CI verte et une revue approuvée avant de fusionner sur main.
  • Un message de commit suit souvent une convention (type(scope): résumé) pour un historique exploitable par les outils.

06 — Claude & GitHub

Un collaborateur de plus dans le graphe de commits

Claude Code utilise les mêmes primitives Git que vous — commits, branches, pull requests — via l'API GitHub, exposée sous forme d'outils MCP.

commit attribué

Chaque commit de Claude porte un trailer Co-Authored-By et un lien de session, pour une traçabilité complète dans git log.

outils MCP GitHub

Lecture et écriture du dépôt (branches, commits, PR, revues) exposées comme des appels d'API structurés, sans quitter la conversation.

veille sur PR

Claude peut s'abonner aux événements d'une pull request (commentaires, échecs de CI) et réagir automatiquement.

  • Les actions à risque (force-push, merge, suppression de branche) demandent toujours une confirmation explicite.
  • Une pull request ouverte par Claude suit le même template et les mêmes règles de revue que toute autre PR.
  • L'historique reste lisible : on peut toujours distinguer qui a écrit quoi, et pourquoi.
